% ─────────────────────────────────────────────────────────────────────────────
\section{Sprint Plan and Deliverables}
\label{sec:sprint-plan}
% ─────────────────────────────────────────────────────────────────────────────

The three implementation sprints are structured around increasing layers of
the system stack: Sprint~1 establishes the foundation layer (contracts,
schema, authentication, and testnet infrastructure); Sprint~2 builds the
lending products, group facilities, and the autonomous AI agent; Sprint~3
closes the loop with decentralised oracles, security hardening, compliance
workflows, and the live simulation. Sprint point totals in v24 reflect all
v23 deliverables \\emph{plus} the new capabilities specified in the
improvement analysis: Sprint~1 rises from 42~to \\textbf{70}~points,
Sprint~2 from 50~to \\textbf{92}~points, and Sprint~3 from 38~to
\\textbf{80}~points.

\section{Justification of Technologies}
\label{sec:tech-justification}
% ─────────────────────────────────────────────────────────────────────────────

This section justifies the selection of each major technology in the CWB
stack. For technologies present in the v23 architecture, only the
v24-modified rationale is noted; the original justifications are preserved
verbatim below. The four v24 additions appear at the end of the section.

\paragraph{Polygon zkEVM Cardona.}
Polygon~zkEVM Cardona is an Ethereum Layer-2 that submits zero-knowledge
validity proofs to Ethereum mainnet, meaning every transaction batch is
cryptographically verified on L1. For a banking prototype, this provides a
materially stronger security narrative than a Proof-of-Stake sidechain: a
malicious operator cannot publish invalid state because the ZK proof would
fail Ethereum's on-chain verifier. Cardona offers EVM equivalence (all
Hardhat / Foundry tooling works without modification), a free public testnet,
and Alchemy RPC support, making it operationally accessible. This replaces
the v23 Polygon~Amoy~PoS testnet while maintaining identical development
tooling.

\paragraph{Solidity 0.8.x and OpenZeppelin Contracts.}
Solidity remains the standard for EVM-compatible smart contracts, supported
by every major security auditing tool (Foundry, Certora, Slither, Echidna).
OpenZeppelin Contracts v5 provides production-audited implementations of
UUPS upgradeable proxies, AccessControl RBAC, ERC-5192 (non-transferable
SBT), and ERC-4337 account abstraction, reducing the bespoke code surface
exposed to audit scrutiny.

\paragraph{PostgreSQL 16 with Row-Level Security.}
Financial ledger data requires ACID transaction semantics, rich integrity
constraints (FK cascades, CHECK constraints), and access-control policies
enforced at the database layer rather than the application layer. PostgreSQL's
Row-Level Security (RLS) enables the append-only \texttt{audit\_logs} policy
that prevents even administrative roles from deleting compliance records.
TimescaleDB --- a PostgreSQL extension --- provides hypertable compression for
the \texttt{MARKET\_DATA} time-series without introducing a separate database
engine.

\paragraph{React~18, Wagmi~v2, and Vite.}
React's component model maps cleanly onto the multi-role banking dashboard
(client view, approver view, admin view, public reserve dashboard). Wagmi~v2
provides typed hooks for EIP-1193 wallet connections, ERC-4337 user-operation
submission, and EIP-712 signing, eliminating the need for low-level
\texttt{window.ethereum} calls. Vite's dev-server proxy avoids CORS
complications between the React SPA, the Express.js backend, and the Alchemy
RPC endpoint during development.

\paragraph{Express.js and FastAPI.}
Express.js handles real-time client interactions over Server-Sent Events
(agent streaming), WebSocket forwarding from Socket.IO, and JWT-authenticated
REST routes. The context-injection layer that prepends per-user on-chain state
into every LLM system prompt is implemented as Express.js middleware, allowing
it to be updated without touching the model serving layer. FastAPI, backed by
Python's scientific ecosystem (scikit-learn, SHAP, networkx), serves the ML
scoring, SHAP explanation, and anomaly detection endpoints at typed REST
boundaries; separation from Express.js keeps the AI/ML stack independently
deployable and replaceable.

\paragraph{ChromaDB for RAG.}
ChromaDB provides a lightweight, file-backed vector store suitable for the
academic prototype's scale (a few hundred policy document chunks). RAG
retrieval latency is benchmarked at $<100$~ms p95 on the demo hardware,
meeting the target set in Section~\ref{sec:llm-eval}. Replacing it with a
hosted vector DB (Pinecone, Weaviate) requires only a client-library swap
because all RAG calls are encapsulated in a \texttt{PolicyStore} abstraction
class.

\paragraph{Hardhat (integration) and Foundry (invariants / fuzzing).}
Hardhat remains the primary deployment and integration-test framework because
its JavaScript environment is familiar to the Web3 community and supports
the project's TypeScript-based deployment scripts. Foundry is adopted
\emph{in addition} for invariant testing and stateful fuzzing because its
Solidity-native test environment catches whole classes of bugs that Hardhat
JavaScript tests cannot (reentrancy under adversarial call sequences,
invariant violations under 10,000 randomly generated execution paths). The
industry practice of combining both frameworks is now standard for any
contract seeking a security audit~[R39].

% ── v24 additions ──────────────────────────────────────────────────────────
\paragraph{Chainlink Functions, Automation, Price Feeds, and Proof of Reserve.}
\emph{(v24 addition.)} The four Chainlink services adopted in v24 serve
distinct roles in the decentralised trust model.
(1)~\textbf{Functions}: runs the ML-score fetch inside a
Decentralised Oracle Network, requiring consensus across independent nodes
before committing the score on-chain; this eliminates the single-operator
trust assumption of the v23 commit-reveal relay.
(2)~\textbf{Automation}: replaces the centralised cron job for overdue
instalment detection with a trustless \texttt{checkUpkeep} /
\texttt{performUpkeep} trigger registered on Cardona, removing the last
centralised component from the loan lifecycle.
(3)~\textbf{Price Feeds}: supplies BDT/USD and ETH/USD via
\texttt{AggregatorV3Interface} with 8-decimal precision, replacing the
governance-approved forex oracle of earlier versions.
(4)~\textbf{Proof of Reserve}: publishes the \texttt{WorldBankReserve} and
\texttt{InsuranceFund} balances to Chainlink PoR feeds, enabling any
external auditor to cryptographically verify reserve backing without
trusting the CWB administrator --- the on-chain analogue of the Merkle-tree
PoR used by major exchanges (Section~\ref{sec:security-analysis}).

\paragraph{The Graph (subgraph event indexing).}
\emph{(v24 addition.)} Polling contract state via RPC for every dashboard
page load is slow (one RPC call per view) and imposes rate-limit pressure
on the Alchemy free tier. The Graph indexes every event the CWB contracts
emit into a GraphQL queryable subgraph, reducing dashboard refresh from
seconds (RPC polling) to tens of milliseconds (subgraph query). The hosted
service supports Polygon~zkEVM~Cardona at no cost for student projects, and
The Graph's sub-second indexing latency makes the Reserve Transparency
Dashboard a genuinely live instrument during the 300-client simulation
(Section~\ref{sec:abm-sim}).

\paragraph{EIP-7702 session keys.}
\emph{(v24 addition.)} The AI agent requires a mechanism to sign on-chain
transactions on the client's behalf after confirmation, without the client
handing over their main private key. ERC-4337 paymasters could achieve
similar delegation but enforce scope at the application level, meaning a
compromised Express.js backend could call any paymaster-permitted operation.
EIP-7702 session keys enforce scope \emph{at the cryptographic key level}:
the key is mathematically incapable of signing transactions outside its
approved tool scope, beyond its 500~USDC value cap, or after its 24-hour
TTL --- these constraints are not policy rules but key properties. This
provides a stronger safety guarantee with a smaller on-chain footprint than
ERC-4337 paymasters for agent-controlled operations, while ERC-4337 is
retained for retail gas sponsorship (its original purpose).

\paragraph{Qwen3-8B with llama.cpp and Model Context Protocol (MCP).}
\emph{(v24 addition.)} Qwen3-8B (Apache~2.0 licence, ~5~GB
Q4\_K\_M quantised) was selected over larger open-source models (Llama-3-70B,
Mistral-22B) because it fits the demo hardware's 16~GB VRAM budget, achieves
$\geq 5$~tokens/s on the AMD Radeon RX~9060~XT (ROCm~6.4 / llama.cpp), and
natively supports tool-calling (MCP) with structured JSON parameter
schemas. The Model Context Protocol constrains the agent to interact with
CWB exclusively through the 16 typed banking tools, preventing arbitrary API
calls or code execution. The privacy-preserving local hosting means client
conversation data never leaves the institution's infrastructure, satisfying
the GDPR data-residency requirement for a Bangladesh deployment without
requiring a consent exemption for cloud AI processing.

\section{Design Patterns Employed}
\label{sec:design-patterns}
% ─────────────────────────────────────────────────────────────────────────────

The following design patterns govern the CWB architecture. Each pattern
is selected because it addresses a concrete failure mode observed in
comparable DeFi projects.

\paragraph{Checks-Effects-Interactions (CEI).}
All state-modifying contract functions follow the CEI ordering: validate
preconditions (Checks), update local state (Effects), then call external
contracts (Interactions). This prevents reentrancy attacks of the class
responsible for the \$60~million DAO hack of 2016 and the \$80~million
Fei Protocol exploit of 2022. The Foundry fuzz suite includes a reentrancy
harness that verifies CEI adherence under adversarial call sequences for
\texttt{disburseLoan}, \texttt{repayInstalment}, and
\texttt{withdrawSavings}.

\paragraph{UUPS Upgradeable Proxy.}
The WorldBankReserve, NationalBankPool, and LocalBankPool contracts are
deployed behind OpenZeppelin UUPS proxies, allowing logic upgrades without
migrating state. The \texttt{\_authorizeUpgrade} function is gated by
GOVERNANCE\_ROLE with a time-lock, so no upgrade can take effect
immediately; this removes the ability for a compromised admin key to deploy
a malicious implementation in a single transaction. The upgrade pattern
also satisfies the Certora verifier's requirement that invariants hold
across \emph{all reachable states}, including post-upgrade states.

\paragraph{Factory Pattern (Local Bank Deployment).}
A \texttt{LocalBankFactory} contract deploys new Local Bank instances via
\texttt{CREATE2} with a deterministic address derived from
\texttt{(nationalBankAddress, bankId)}. This enables the National Bank
Admin to onboard a new Local Bank in a single transaction without
deploying contracts manually, and allows the World Bank to predict the
address of any Local Bank from its ID before deployment.

\paragraph{Observer Pattern (Event-Driven Architecture).}
All significant state transitions emit indexed events. The event log is the
authoritative on-chain audit trail; no state is inferred from the absence
of events. This decouples producers (contracts) from consumers (The Graph
subgraph, React dashboard, Tenderly monitors, AGENT\_ACTION\_LOG recorder)
without introducing tight coupling or blocking calls.

\paragraph{State Machine (Loan Lifecycle).}
\texttt{LoanController} implements an explicit state machine with
transitions guarded by access-control modifiers and oracle preconditions:
DRAFT $\to$ PENDING\_KYC $\to$ PENDING\_SCORE $\to$ PENDING\_APPROVAL
$\to$ ACTIVE $\to$ \{CLOSED, DEFAULTED\}. Invalid transitions revert with
a named error code (\texttt{LoanController\_\_InvalidState}). This makes
the frontend Transaction-State Machine of Section~\ref{sec:tx-state-machine}
a faithful projection of the on-chain state rather than an independent UX
model that can diverge.

\paragraph{Commit-Reveal (ML Oracle Integrity).}
The ML score is committed on-chain as $h = \mathrm{keccak256}(s \,\|\,
\text{nonce})$ before it is revealed. This prevents the oracle operator from
tailoring the revealed score to a known loan application after seeing
approval intent. The Chainlink Functions upgrade (US-3.11) supersedes this
pattern for the primary oracle path, but the commit-reveal endpoint is
retained as a prototype-phase fallback, ensuring the LoanController state
machine never depends on network availability of the Chainlink DON.

\paragraph{Repository Pattern (Off-Chain Data Access).}
All database access from Express.js goes through typed repository classes
(\texttt{LoanRepository}, \texttt{ClientRepository},
\texttt{AgentActionRepository}). Repository interfaces are injected via the
Express.js dependency injection container; tests substitute in-memory
repositories, eliminating the need for a live database in the Hardhat
integration test suite. This also isolates the PostgreSQL schema migrations
from the API layer, so a schema change requires updating the repository but
not the route handler.

\paragraph{Circuit Breaker (Emergency Pause).}
Each contract inherits OpenZeppelin \texttt{Pausable}. The GOVERNANCE\_ROLE
can pause a single contract (granular pause) without halting the entire
system. A COMPLIANCE\_ROLE pause-trigger fires automatically from the
Tenderly alert when a reserve-ratio breach is detected. Every paused state
emits a \texttt{Paused(address account)} event consumed by both the
Tenderly monitor and the SAR workflow (Section~\ref{sec:regulatory-compliance}).

\section{Software Testing Strategy}
\label{sec:testing}
% ─────────────────────────────────────────────────────────────────────────────

\begin{figure}[H]
\centering
\OnePageDiagram{fig-testing-pyramid.pdf}
\caption{CWB software testing pyramid. The base layer (Foundry unit + fuzz
tests and Hardhat integration tests) runs in CI on every pull request. The
middle layer (end-to-end tests and the Foundry simulation) runs pre-merge.
The apex (formal verification and red-team security tests) runs at sprint
boundaries.}
\label{fig:testing-pyramid}
\end{figure}

The testing strategy follows a test pyramid structure: a broad base of
automated unit tests that run quickly, a middle tier of integration and
system tests, and a narrow apex of formal verification and adversarial
security tests that run at sprint boundaries.

\paragraph{Unit testing --- Foundry and Hardhat.}
Every smart-contract function is tested in two frameworks:
\begin{itemize}[noitemsep]
\item \textbf{Foundry} (\texttt{forge test}): Solidity-native unit tests
with stateful fuzzing (10{,}000 runs per invariant). Foundry tests cover
access-control reverts (non-APPROVER\_ROLE calls to \texttt{approveLoan}),
arithmetic edge cases (zero-amount loans, maximum USDC amounts), state
machine guards (transition from wrong state reverts with correct error),
and the three cross-cutting invariants
(Section~\ref{sec:foundry}).
\item \textbf{Hardhat + Ethers.js}: TypeScript integration tests deploy the
full contract hierarchy to a local Hardhat network and run scenario-level
tests (apply loan $\to$ score $\to$ approve $\to$ repay $\times N$) with
Chai assertions on emitted events and final balances.
\end{itemize}

\paragraph{Integration testing.}
Integration tests span the contract $\leftrightarrow$ Express.js
$\leftrightarrow$ FastAPI boundary. Supertest drives the Express.js API
against a live Hardhat local network; FastAPI is stubbed with
\texttt{respx} mocks returning deterministic risk scores. Integration tests
cover the full EIP-712 login $\to$ JWT $\to$ authenticated loan-apply
$\to$ ML oracle callback $\to$ approval notification flow for all actor
roles defined in Section~\ref{sec:actor-taxonomy}.

\paragraph{System and end-to-end testing.}
The 300-client Foundry simulation (US-3.15) constitutes the primary system
test: it exercises the complete four-tier capital flow, the instalment
lifecycle, the fraud-rate stress scenario, and the reserve-ratio
dashboard in a single deterministic run. A separate Playwright
end-to-end suite drives the React frontend against the Cardona testnet,
covering wallet connection, loan application submission, approver
dashboard interaction, agent chat (read tools), and confirmation-gate
flow (write tools). Playwright tests record a video artefact for the
live demo.

\paragraph{Security testing --- fuzz, invariants, and Certora.}
\begin{itemize}[noitemsep]
\item \textbf{Foundry stateful fuzzer}: 10{,}000 fuzz runs per invariant;
counterexamples are saved as deterministic replay tests that fail CI on
regression. The no-privileged-exemption test (US-3.16) and the
\texttt{freezeAccount} invariant (US-3.18) run as part of this suite.
\item \textbf{Certora Prover}: two CVL specifications verified against
\texttt{WorldBankReserve} (reserve never under-collateralised; no
over-allocation downstream). The prover is run at the Sprint~3 gate; any
unresolved counterexample blocks the sprint delivery
(Section~\ref{sec:certora}).
\item \textbf{Slither static analyser}: run in CI on every contract change;
high-severity findings block merge. Medium and informational findings are
reviewed and documented with accept / fix decisions in the security log.
\item \textbf{Session key scope enforcement}: the ten test scenarios of
Section~\ref{sec:llm-eval} (Item~6) are automated as a Foundry test that
attempts to sign transactions with an out-of-scope session key and asserts
\texttt{EIP7702\_\_ScopeViolation} revert in all cases.
\end{itemize}

\paragraph{LLM red-team testing.}
The adversarial evaluation protocol of Section~\ref{sec:llm-eval} is
executed as a scripted test sequence:
\begin{itemize}[noitemsep]
\item \textbf{Regulatory hallucination} (50~prompts): target $100\%$
refusal-or-defer rate.
\item \textbf{Human-gate bypass} (20~prompts): target zero-bypass rate;
any write-tool execution without a prior confirmation turn is a
critical failure that blocks sprint delivery.
\item \textbf{Action accuracy} (50~scenarios): target $\geq 95\%$ correct
tool identification and parameter assembly.
\end{itemize}
Red-team results are logged in \texttt{AI\_ML\_SECURITY\_LOG} and reviewed
against the evaluation thresholds before the final thesis submission.

\paragraph{Gas benchmarking.}
Every contract function is benchmarked with Foundry's
\texttt{--gas-report} flag. Target ceilings: \texttt{applyLoan}
$\leq 120{,}000$~gas; \texttt{approveRisk} (with oracle commit)
$\leq 80{,}000$~gas; \texttt{repayInstalment} $\leq 60{,}000$~gas.
Gas costs are converted to USD at the spot ETH/USD Chainlink price feed
rate and reported in Table~\ref{tab:gas-costs}. This converts gas
benchmarking from an informal note into a reportable empirical finding
for RQ2.

\paragraph{Continuous integration.}
All tests run in a GitHub Actions CI pipeline triggered on every pull
request to \texttt{main}. The pipeline stages are: (1)~Slither static
analysis; (2)~Foundry unit + fuzz suite (\texttt{forge test}); (3)~Hardhat
integration tests; (4)~FastAPI ML service unit tests (pytest); (5)~React
component tests (Vitest). Certora and Playwright end-to-end tests run
on a separate workflow triggered at sprint-close tags. A failing CI
pipeline blocks merge; the policy is enforced at the GitHub branch-protection
level.
